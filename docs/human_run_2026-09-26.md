## Result

The run proves that the live components can operate in one persistent session:

1. Whisper transcribed human microphone recordings.
2. Granite selected the intended tool in all seven completed tool-intent trials.
3. Calculator expressions were normalized before execution.
4. Every selected tool completed successfully in those seven trials.
5. Every result was accepted by the controller and submitted at a later MiniCPM input boundary.
6. The native log proves six submitted contexts entered ordinary LLM prefill. The seventh submission is recorded by the HTTP adapter, but the copied server log ends mid-line before its corresponding native prefill was flushed to disk.
7. MiniCPM generated audible speech in the persistent session.

The run does **not** yet prove the target chain “current spoken request → current tool result → correct spoken answer.” In every completed tool trial that generated assistant text, generation began before the current tool result was available. Correct answers on repeated questions are therefore not causally attributable to the current call. The most likely explanation is a one-turn delayed response to a previously injected result.

### Latency

- Eight completed turns: mean 3.77 s, median 3.45 s, range 2.61–7.14 s.
- Seven completed tool turns: mean 3.29 s, median 3.22 s.
- After the first post-restart Granite warm-up, routing from completed transcription to tool completion was about 0.94–1.16 s. The warm-up tool call took 2.11 s.
- Local deterministic tool execution took less than 1 ms per call.
- Controller acceptance to context submission took about 6–7 ms when the audio loop had reached a boundary. When Granite completed during remaining audio chunks, submission waited another 138–195 ms for a boundary.
- Native audio encoding was generally 18–51 ms per one-second input frame after warm-up.
- Logged Token2Wav real-time factors were roughly 0.17–0.37, so synthesis itself was faster than real time.

The principal latency problem is response coordination, rather than calculator/lookup execution or vocoding.

## Why the spoken answers lagged

The current voice path does this:

1. Transcribe the entire recording.
2. Start Granite routing in parallel.
3. Feed every one-second audio chunk to MiniCPM and decode after each chunk. A result that is already queued is automatically attached to the next audio prefill.
4. After all recorded chunks, wait for Granite and the tool if they are still running.
5. If a result is still queued, submit it using one silence boundary and decode once.
6. Stop adding silence as soon as the scheduler queue is empty, including immediately after a successful submission.
7. Collect whatever TTS files appeared during the turn.

MiniCPM often started speaking during step 3, before Granite finished. In the last three trials the result did enter a later microphone chunk, so the boundary queue itself worked. MiniCPM nevertheless returned to listening after that prefill. The code did not continue controlled decoding until a post-result answer appeared. The next human recording then stimulated speech based on the previous result. This produces the observed pattern:

```text
room result submitted → no answer
same room question → correct room answer before new room result
calculator question → stale room answer before calculator result
same calculator question → calculator answer before new calculator result
```

This is a response-attribution and scheduling problem. It is separate from Granite accuracy and tool execution.

## Audio and logging defects found

1. **TTS filename reuse after native restart.** The native server reused names such as `wav_4000.wav` in a persistent output directory. `_new_tts()` detects only new path names, so an overwritten path can be omitted. The 1.44 s combined audio for the first successful room lookup appears to omit the overwritten 0.84 s first chunk.
2. **Turn attribution is too coarse.** `model_text` joins all text emitted while microphone chunks and the context boundary are processed. It does not label text as pre-result or post-result.
3. **Job-to-trial lineage is incomplete.** Submitted audio uses a Gradio job ID, while the completed trial gets a new unrelated trial ID. Most submitted recordings therefore cannot be deterministically mapped to their trial record from the export alone.
4. **Verdicts use mutable `last_trial_id`.** Repeated clicks create duplicate rows, and the UI retains old notes. A verdict should carry the displayed trial ID explicitly and support one current revision per trial.
5. **Append-only directories mix runs.** The main controller log contains dates from two separate runs. Every experiment should get a unique run directory and manifest.
6. **Server log was copied while active.** `minicpm_server.log` ends mid-line during counter 41. The final native context prefill and final TTS completion are absent even though their files and controller completion record exist.
7. **Exact room lookup is brittle to ASR.** “robotic seminar” failed while “robotics seminar” succeeded. The tool should log a declared alias normalization or controlled fuzzy match, preserving both raw and normalized arguments.
8. **Missing reference-audio path.** Both server logs warn that `tools/omni/assets/default_ref_audio/default_ref_audio.wav` could not be loaded. Speech was still generated through the Token2Wav prompt cache, but this warning should be removed or the absolute asset path supplied before speech-quality evaluation.

The `n_ctx_seq=8192 > n_ctx_train=4096` warning applies to the TTS model configuration. The observed session reached only about 734 LLM positions, so this run did not approach that limit.

## Required changes before the next human run

1. Keep the existing next-boundary drain, but log whether submission used a microphone or silence boundary and identify its exact response epoch.
2. After a context submission, continue controlled silence-boundary decode until post-submission text/audio, an observable end state, or a clear deadline. Log every added boundary. Do not stop merely because the scheduler queue became empty.
3. Record assistant text and TTS chunks in separate `pre_result` and `post_result` fields. The success criterion must use only post-result output.
4. Give each native server start a unique output directory or clear/archive `tts_wav` before starting. Detect new audio by modification generation as well as path.
5. Use one ID across submitted audio, trial trace, combined audio, and verdict. Save verdict revisions deterministically and clear the old note field.
6. Add a run manifest with adapter Git tag, native commit, patch hash, model identifiers, GPU placement, and start/stop timestamps.
7. Add declared room-name alias normalization for the observed ASR singular/plural error.
8. End the server cleanly and flush/copy logs only after the run.

## Next acceptance gate

A trial counts as the core demonstration only when all of these are present for the same stable trial ID:

1. human microphone audio and committed ASR transcript;
2. model-selected tool and validated arguments;
3. successful tool result;
4. context submission and, when available, evaluation evidence;
5. assistant text generated after that submission containing the correct fact;
6. returned audio derived from those post-submission TTS chunks;
7. a human verdict confirming the correct answer was audible.

Repeated identical questions can be useful diagnostics, but they cannot establish current-turn causality in a persistent session unless pre-result and post-result outputs are separated.
